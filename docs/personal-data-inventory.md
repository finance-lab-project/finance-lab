# Personal data inventory

Repository baseline for issue #105. The public policy at `/privacy` is linked before the sign-in fields and from the shared footer. The inventory describes application behavior and the documented pilot backup procedure. Live host settings were outside this review.

| Surface | Fields and purpose | Recipients and storage | Retention and deletion |
| --- | --- | --- | --- |
| Self-registration | No form, endpoint or registration fields. The operator preconfigures the pilot owner. | No registration store or recipient. | No registration records to delete. |
| Sign-in and forms | Submitted username and password for authentication. Configured username and bcrypt hash for verification. Session identifier and CSRF token maintain login and protect form submissions. | Spring Security on the pilot server. The browser receives the session cookie and form token. The server keeps session state in memory. The operator manages the configured pilot account. | Submitted password is used for verification and is not stored in SQLite. Sessions end at logout, idle expiry or restart. The operator replaces the configured hash when rotating access. Password rotation leaves the owner’s budget records in place. |
| Budget forms | Owner key and periods, category codes and names, settings and planned amounts, actual spending, income and contributions, recording flags and revisions, reconciliation dates and balances, dated cash movements, investment account names and IDs, product types, closing values and credited income, FIRE targets and linked accounts. Used to calculate and preserve the owner’s budget and reports. | Owner-scoped reads and writes in SQLite. The pilot operator manages the VM, database and recovery. The [backup procedure](sqlite-backup.md) documents encrypted SQLite snapshots in private Yandex Cloud Object Storage. | No automatic expiry or account erasure in the application. Edits update live records. Copies can retain prior values. Backup expiry and erasure require an owner decision. |
| Backup verification reference | Empty-budget flag or month, category code, planned amount, actual spending, opening buffer and yearly spending. The backup service compares these figures with the snapshot, and operators use them to verify restores. | The runbook specifies a private, root-owned `backup-reference.json` on the pilot VM with mode `0600`. The pilot operator maintains it and the backup service reads it. | Update after edits that affect the figures. The runbook specifies no expiry or deletion process. The owner and operator must decide when to delete the file and how to handle it on pilot shutdown or a deletion request. |
| Backup operations record | Each retained run receipt contains the backup object key and checksum. The record also keeps the exact reference used for that run, including any saved figures, to identify and verify the corresponding backup during recovery. | The runbook specifies a protected operations record off the VM for authorized pilot operators. The operator must confirm its storage location and access controls. | The runbook specifies no retention period or deletion process. The owner and operator must decide when to remove receipts and historical references, including when backups expire or budget data is deleted. |
| Application diagnostics | Framework and server messages can include timestamp, severity, process or thread, logger, diagnostic message and exception details. Used to diagnose startup and runtime failures. No application-defined request body, sign-in event or budget-value logging. HTTP access logging is not enabled by repository configuration. Exception messages can reflect request context. | Application console and operator-managed logging on the host. No log exporter configured in the application. Live proxy, host journal and any forwarding need operator confirmation. | The app defines no log retention or deletion job. The operator must confirm rotation, storage, access and deletion on the host and proxy. |
| Analytics | No analytics client, event collection endpoint, tracking cookie or session replay in the app. Browser scripts submit budget operations to the same app. | No analytics recipient or store in the app. | No analytics records to expire or delete. |

## Open owner and legal decisions

- Confirm the responsible operator or legal entity, applicable processing basis, and contact for access and deletion requests before approving the policy for external use.
- Confirm live access to private Yandex Cloud Object Storage and timer activation during pilot cutover. Confirm storage and access for the off-VM record and approve retention and deletion for both verification copies.
- Confirm live proxy and application log fields, recipients and access, rotation and deletion. In particular, check whether the proxy records IP addresses, request targets or referrers. Confirm backup retention and the process for deleting budget data from live storage and expiring copies, including how restores handle previous deletions.
- Before introducing registration or analytics, approve the fields, purpose, recipients, retention and deletion for that collection. Update the inventory and public policy and link the notice from the collection surface before enabling it.
- Keep passwords, hashes, cookies, CSRF tokens, budget values, account labels and other identifying data out of telemetry and shared screenshots. Use synthetic accounts and budget fixtures for verification.

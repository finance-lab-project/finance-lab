## Dated timeline

### 19 September–19 October 2026 · Early frontend and AI-assisted prototype

- **19 September, documented.** The original repository contains a Vite, React and TypeScript initialization commit. Anton identified this repository as the project's starting point. That identification is author recollection. The commit establishes the frontend baseline. The scope and persistence behavior of any React/localStorage experiment, and its relationship to the AI work, remain unverified here. [Initialization commit][frontend-init]
- **6–10 October, documented and reported.** A separate Python learning prototype contained a Yandex AI Studio adapter. The dated run note reports Anton making a live request using `yandexgpt-5.1` with a synthetic budget. PR #3 credits Codex with implementation and test assistance. The offline tests and the reported live model call provide separate evidence. PR #4 adds a validated read-only `get_budget` call over synthetic fixtures. The components were the Python prototype, model adapter and synthetic budget tool. The record establishes Yandex AI Studio's role as model provider for the experiment. Yandex authorship of application code, integration with real financial data and a production deployment are unverified. [Run record][live] · [Adapter][adapter] · [PR #3][agent3] · [PR #4][agent4]
- **19 October, documented.** ADR-026 explicitly names the Python repository as the learning prototype. It describes a planned product agent with least privilege and human-approved writes and distinguishes that plan from engineering assistance. **Interpretation.** The read-only fixture kept the experiment scoped to learning how to call the model and validate a tool request. The records do not establish why Yandex was selected over other providers, what the experiment cost, or whether it influenced the choice of the subsequent Vaadin stack. [ADR-026][adr]

### 5–10 November 2026 · Java/Vaadin modular monolith

- **5–10 November, documented.** The app decision describes a Java modular monolith with a Vaadin UI, no Spring, a custom ORM and PostgreSQL using Anchor Modeling. The design put the Budget UI and application logic in one Java application with persistence through the custom mapping layer. **Interpretation.** This kept application delivery within one deployable while giving the team control over the mapping to the chosen data model. The available evidence does not establish the full selection rationale or alternatives considered. [Architecture decision][vaadin]
- **By 10 November, reported.** App PR #16 records PostgreSQL and ORM integration checks. App PR #12 records the Budget release on 10 November and live acceptance checks. These records support a working Budget release and exercised persistence path within the scope of those checks. In his later account, Anton places the previous live PostgreSQL app on Yandex Cloud. Exact topology, traffic, latency, reliability and operator time remain unverified. [ORM PR #16][app16] · [Budget PR #12][app12] · [Author's retrospective](linkedin-post.md)
- **Overhead and revision.** The custom ORM required a mapping layer and PostgreSQL integration checks. A PostgreSQL-backed setup also requires managing database access, upgrades and backups or using a managed service, as the later decision explains. On 14 November, the one-owner pilot decision selected embedded SQLite under a durable-disk and infrequent-write assumption. **Interpretation.** This reduced the number of services needed for the pilot. Evidence is missing for actual time or money saved and for whether Vaadin or the ORM independently drove the revision. [ORM PR #16][app16] · [14 November decision][spring]

### 14–21 November 2026 · Spring Boot / Spring MVC / Thymeleaf / SQLite

- **14 November, documented.** PR #8 accepted a single Spring Boot application for an online, one-owner pilot. Desktop and phone browsers use responsive HTML generated by Spring MVC and Thymeleaf. The server owns validation, budget calculations and saves through JDBC to SQLite on persistent local disk. The goal was to save a monthly total once and read the same saved state from either device. The screen walkthrough reached desktop setup. Prepared screens covered additional paths, and the decision called for a working save to test arbitrary input, persistence and cross-device use. [Decision PR #8][spring8] · [Accepted decision][spring] · [Walkthrough notes](../budget-v1-prototype-review.md)
- **Rationale and overhead, documented.** The decision describes occasional short writes and one application instance with durable storage, making SQLite's serialized writes acceptable for the pilot. The shared forms and server-side database avoid a separate database service and offline synchronization. The remaining work includes driver and schema updates, durable storage, backups and recovery checks. The decision identifies frequent write contention or loss of durable local disk as reasons to revisit PostgreSQL. These are design trade-offs. Comparative performance and operating costs were not measured in the cited records. [Accepted decision][spring]
- **21 November, reported.** The v0.1.0 release records deployment of revision `220cfdb47b737f248192b396dbf5c3185407ac3a`, 20 passing Maven tests in CI, HTTPS sign-in, synthetic save and readback on desktop and a physical phone, and persistence after an application restart. It also reports decrypting a downloaded SQLite backup and verifying its integrity. The release includes an empty budget at first use, monthly plans and spending, historical entry and a yearly overview. These checks cover the release conditions described. Long-term usage, performance and recovery outcomes remain unverified. No subsequent architecture replacement is established by this timeline. [Release record and linked CI run][release] · [Deployed revision][revision]
